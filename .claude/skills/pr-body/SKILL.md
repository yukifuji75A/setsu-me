# PR本文・コミットメッセージ作成

## 作成フロー

1. 対象ブランチの差分を実際に確認する（`git diff` / `git diff --stat`）。会話の記憶だけで変更内容を書かない。
2. 差分と実装の経緯を踏まえて、下記テンプレートに沿った本文を作成する。
3. Markdown記法で、markdownのコードブロックで囲んで提示する。そのままコピペして使える形にする。
4. 複数回のやりとりで実装を追加した場合は、追記分だけを求められたら追記分のみ、全体を求められたら今までの変更をすべて含めた本文を提示する。どちらを求めているか曖昧なら確認する。

## PR本文テンプレート

```markdown
## 概要（実装内容）

〜何を実装・修正したかを箇条書きで〜

### 変更ファイル

- `path/to/file`
  - 〜そのファイルで何を変えたか〜

## 設計理由

〜なぜこの構造・アーキテクチャを選んだかの説明〜
〜実装方法が複数あった場合、なぜこちらを採用したかの比較理由〜

## 判断理由

〜個別の仕様・UX上の分岐をどう決めたか、なぜそう決めたかの説明〜

Closes #(issue番号)
```

- 「設計理由」と「判断理由」は役割が異なるので分けて書く。
  - **設計理由**：構造・アーキテクチャ上の選択（例：ロジックをモデルに集約した理由、専用のサービスクラスに切り出した理由）。実装方法が複数考えられた場合に、なぜその方法を選んだかという比較の理由もここに含める。
  - **判断理由**：個別の仕様・UX上の分岐決定（例：このボタンを残すか消すか、このケースは対応するか見送るか）。
- 上記4つ（概要／変更ファイル／設計理由／判断理由）以外の見出し（テスト方針、影響範囲など）が必要な場合は、同じ「## 見出し」形式で必要な分だけ追加してよい。無理に4つに収めようとしない。
- 実装中に見つかった不具合や、本来のタスクに付随して直した箇所も「概要」の箇条書きに含める。
- 検討したが今回は対応しないと決めた事項（スコープ外対応）があれば、対応しなかったことと理由を書き残す。
- 本文の最後に`Closes #(issue番号)`を必ず入れる。issue番号はユーザー自身が記入するため、`(issue番号)`の部分はプレースホルダーのまま残す。

## 追加コミットのルール

一度コミットした後、エラーの修正などで追加のコミットが必要になった場合は、コードの修正が終わった後に、以下を含むコミットメッセージ案を提示する。ユーザーがGitHub上でコミットメッセージを入力する際に、そのまま参照できるようにするため。PR本文と同様、markdownのコードブロックで囲んで提示する。

- 追加のコミットが必要になった原因（何が、なぜ問題だったか）
- その修正で実装・変更した内容

エラー対応に限らず、同じPR内で後から追加の修正コミットを行う場合は同様に扱う。

## 文体ルール

- 常体（「〜した。」「〜である。」）で統一する。「です・ます調」は使わない。
- プログラミング初心者（卒業制作レベル）が読んでも理解できる平易な表現にする。専門用語を使う場合は、必要最低限にし、文脈で意味が伝わるようにする。
- 「〜と思われる」「〜かもしれない」のような曖昧な推測表現は避け、実際に確認した事実として書く。
